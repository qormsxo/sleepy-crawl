# Sleepy Crawler — 계획 4: 관리자 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (user chose inline). Steps use checkbox (`- [ ]`) syntax.

**Goal:** 관리자 한 명이 로그인해서 검토 대기 글을 처리하고, 게시글·제보·커뮤니티·키워드·밈·프롬프트·설정을 배포 없이 관리하며, 수집 현황을 대시보드로 본다(설계 7-12, 지시서 7장).

**Architecture:** `/admin` 아래 서버 컴포넌트 화면 + 서버 액션. 로직은 `src/admin/*.ts`에 프레임워크 없이 두고 PGlite로 테스트한다. 세션은 DB(`admin_sessions`, 토큰 해시만 저장) + HttpOnly 쿠키. **권한 검사는 모든 관리자 화면과 모든 서버 액션에서 직접** 한다(Next 16 문서: proxy는 사전 확인용일 뿐 인증 수단이 아님). Cache Components 때문에 세션을 읽는 부분은 `<Suspense>` 안에 둔다. 재평가처럼 오래 걸리는 일은 관리자 요청을 `reeval_requests`에 넣고 워커가 처리한다.

**Spec:** 설계 문서 7-8(재평가·비교), 7-12, 8, 10. 결정: `docs/decisions.md`.

## 이 계획의 결정

1. **비밀번호 해시는 Node 내장 `scrypt`**(외부 네이티브 모듈 없음). 설계 문서의 argon2 대신 — Windows 개발 환경에서 네이티브 빌드를 피하기 위해.
2. **최초 관리자 계정:** `npm run admin:create -- <email>`. `ADMIN_PASSWORD` 환경변수가 있으면 그 값, 없으면 무작위 비밀번호를 만들어 한 번만 출력. 비밀번호를 명령줄 인자로 받지 않는다(셸 기록에 남음).
3. **세션:** 무작위 32바이트 토큰, DB에는 SHA-256 해시만, 7일 만료, 쿠키 `sc_admin`(HttpOnly, SameSite=Lax, 운영에서 Secure). 로그아웃 시 DB 행 삭제.
4. **로그인 시도 제한:** IP 해시 기준 15분에 실패 5회면 막음(`admin_login_attempts`).
5. **관리자 수동 변경:** 상태·점수·분류를 바꾸면 `status_source = ADMIN`(이후 자동 평가가 덮어쓰지 않음). `PUBLISHED`로 바꾸면 `published_at` 설정(이미 있으면 유지).
6. **재평가는 비교용:** 선택한 프롬프트 버전으로 평가를 새로 만들되(`purpose = REEVAL`) 글의 공개 상태는 바꾸지 않는다(설계 7-8). 본문은 글 페이지를 다시 정중하게 요청해 얻고, 실패하면 제목·미리보기로 평가. 수동 제보 소스는 요청하지 않음.
7. **커뮤니티 "등록"은 이미 코드에 있는 어댑터의 설정 행 추가**다(설계 7-12). 삭제는 수집 기록이 없을 때만, 아니면 비활성화.
8. **변경 이력:** 모든 관리자 변경을 `admin_audit_log`(누가, 무엇을, 전후 요약)에 남긴다.
9. **화면은 단순하게:** 표 + 폼. 디자인은 공개 화면의 어두운 테마를 따른다.

## Global Constraints

- 관리자 서버 액션은 첫 줄에서 `requireAdmin()`(세션 확인, 실패 시 throw/redirect).
- 외부 텍스트(제목·제보 설명 등)는 텍스트로만 렌더링.
- 설정·키워드·프롬프트는 DB에서만 읽는다(기존 원칙).
- 재평가도 LLM 일일 예산(`daily_eval_limit`)을 지킨다.

## Review Focus

1. 로그인하지 않은 요청이 관리자 서버 액션을 직접 호출 → 거부(화면 숨김만으로 막지 않음).
2. 비밀번호 6번 틀림 → 15분 차단, 맞는 비밀번호도 그동안 거부.
3. 관리자가 HIDDEN으로 바꾼 글 → 이후 재평가·자동 평가가 상태를 바꾸지 않음.
4. 프롬프트 버전 활성화 → 활성 버전은 항상 정확히 1개(동시에 두 번 눌러도).
5. 커뮤니티 설정 JSON에 잘못된 값(lists가 문자열 등) → 저장 거부, 기존 설정 유지.

### Task 1: 관리자 계정·세션·로그인 시도 (로직)
`src/admin/auth.ts`: `hashPassword(pw) / verifyPassword(pw, stored)`(scrypt, 솔트·파라미터 포함 문자열), `createAdmin(db, email, password)`, `login(db, email, password, ipHash, now) → { ok: true; token } | { ok: false; error: 'invalid' | 'locked' }`, `sessionFromToken(db, token, now) → admin | null`, `logout(db, token)`. 테이블 `admin_users`, `admin_sessions(token_hash, admin_id, expires_at)`, `admin_login_attempts(ip_hash, at, success)`, `admin_audit_log`. CLI `admin:create`.
테스트: 해시 검증·잘못된 비밀번호, 세션 만료, 5회 실패 후 차단(맞는 비밀번호도), 15분 뒤 해제, 토큰 원문은 DB에 없음.

### Task 2: 로그인 화면과 보호
`src/lib/admin-session.ts`: `currentAdmin()`(쿠키 → 세션, `cache`로 요청 내 1회), `requireAdmin()`(없으면 `/admin/login`으로 redirect; 서버 액션에서는 throw). `/admin/login`(폼, 서버 액션), 로그아웃, `/admin/layout.tsx`(Suspense 안에서 확인 후 메뉴). 테스트: 로그인 폼 컴포넌트, 액션이 세션 없이 호출되면 거부(Review Focus 1).

### Task 3: 게시글·검토 대기
`src/admin/posts.ts`: `listPosts(db, { status?, sourceKey?, cursor })`, `postDetail(db, id)`(평가 이력, 제보 설명, 발견 경로), `updatePost(db, adminId, id, { status?, score?, categories? })`(ADMIN 표시, 공개 시각, 감사 로그). 화면 `/admin/posts`(기본: REVIEW), `/admin/posts/[id]`. 테스트: 상태 변경·ADMIN 표시·published_at·이후 evaluatePost가 덮어쓰지 않음(Review Focus 3).

### Task 4: 제보 목록
`listSubmissions(db, { status? })`(제보 설명·유형·결과·연결 글). 화면 `/admin/submissions`. 테스트: 필터, IP 해시는 화면 데이터에 포함하지 않음.

### Task 5: 대시보드
`src/admin/stats.ts`: `dashboardStats(db, now)` → 누적 수집·평가 완료·공개·검토 대기·비공개 수, 커뮤니티별 수집량, 한국/Reddit 비중(목표 80:20 대비 실제), 수집 경로별(건수·평균 점수·공개 비율), 최근 실행 20건과 오류, 오늘 평가 수·토큰. 화면 `/admin`. 테스트: 고정 데이터로 각 수치.

### Task 6: 커뮤니티 관리
`src/admin/sources.ts`: `updateSource(db, adminId, id, { status?, intervalOverride?, config?, statusReason? })`(config는 zod로 검증: `lists`는 URL 배열, `maxDetailFetches` 양의 정수, `manualSubmission` boolean), `createSource`(등록된 어댑터 키만), `deleteSource`(기록 없을 때만), `unpauseSource`. 화면 `/admin/sources`, `/admin/sources/[id]`(최근 오류 50건). 테스트: Review Focus 5, 삭제 제한, 미등록 어댑터 거부.

### Task 7: 키워드·밈·설정
`src/admin/keywords.ts`: CRUD(종류, 키워드, 유사 표현, 설명, 시작·종료일, 활성, 우선순위), 중복(kind+keyword) 거부. `src/admin/settings.ts`: 허용된 키만, 타입·범위 검증(예: `followup_until_hour` 3~24). 화면 `/admin/keywords`, `/admin/settings`. 테스트: 검증·감사 로그.

### Task 8: 프롬프트 버전·재평가·비교
`src/admin/prompts.ts`: `createVersionFrom(db, adminId, baseId, edits)`(배점 6개 키·임계값 검증), `activateVersion(db, adminId, id)`(트랜잭션 + 부분 유니크 인덱스로 항상 1개, Review Focus 4), `requestReeval(db, adminId, versionId, { postIds | recent: n | status })` → `reeval_requests`. `evaluatePost`에 `{ promptVersionId, purpose: 'REEVAL' }` 옵션: 평가 행만 만들고 글은 그대로. 워커 tick이 요청을 회차당 최대 10건 처리(예산 준수). `compareVersions(db, a, b, postIds?)` → 글별 A/B 점수·분류·결정·이유, 결정이 바뀐 글 표시. 화면 `/admin/prompts`, `/admin/prompts/[id]`(편집·활성화·재평가 요청), `/admin/prompts/compare?a=&b=`. 테스트: 활성화 원자성, REEVAL이 글 상태를 안 바꿈, 비교 결과.

### Task 9: 실제 확인과 문서
로컬 DB 마이그레이션, 관리자 계정 생성, 브라우저로 로그인 → 검토 대기의 DC 제보 공개 처리 → 피드 노출 확인 → 키워드 추가 → 프롬프트 새 버전 → 재평가 2건(Gemini) → 비교 화면. `docs/phases/phase-4.md`, README.
